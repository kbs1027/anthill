anthill 1단계 구현 계획

구현 작업 12개를 우선순위 순서대로 정리했습니다. 위의 순서도로 전체 흐름을 보고, 아래 카드에서 작업마다 왜 그 순서인지, 무엇이 끝나야 시작하는지, 핵심 로직이 어떻게 도는지, 끝나면 무엇이 확인되는지를 봅니다.

원문: docs/superpowers/plans/2026-11-05-phase1-chart.md · 설계: docs/superpowers/specs/2026-11-04-phase1-chart-design.md

00순서와 우선순위

순서는 "기준이 되는 것부터" 정했습니다. 먼저 모든 서비스가 같이 쓰는 바닥(골격, 공통 계약, 이벤트 전송)을 고정합니다. 다음으로 정확도의 근거인 업비트 원본을 가져오는 어댑터를 만들고, 그 값으로 차트 데이터를 맞추는 marketdata를 만듭니다. 그 뒤에 브라우저 입구와 화면을 만들고, 마지막에 실제 업비트와 24시간 대조합니다. 숫자를 누르면 해당 작업으로 갑니다.

1
기반

개발 환경과 멀티 프로젝트 골격

왜 이 순서

모든 작업이 올라설 바닥이다. 버전(JDK 25, Spring Boot 4.1.2, PostgreSQL 18)과 모듈 경계를 처음에 못 박아야 이후 작업이 같은 전제 위에서 움직인다.

먼저 끝나야 하는 작업

없음

끝나면 확인되는 것

세 서비스가 각각 뜨고(contextLoads), marketdata가 PostgreSQL 18에 테이블 5개를 만든다. ./gradlew build 통과.

틀리기 쉬운 상황 —
2
기반

공통 계약 libs/market-contract

왜 이 순서

서비스 셋이 똑같이 쓰는 타입(종목 ID, 캔들 단위·경계, 캔들, 숫자 규칙, 이벤트 형식)을 먼저 고정한다. 여기가 흔들리면 서비스끼리 형식이 어긋난다.

먼저 끝나야 하는 작업

1

끝나면 확인되는 것

캔들 경계 계산과 숫자 규칙이 테스트로 고정되고, 숫자가 JSON 문자열로 정확히 오간다.

틀리기 쉬운 상황 같은 값, 다른 자릿수
3
기반

이벤트 전송 libs/event-bus

왜 이 순서

서비스 사이 비동기 통신의 바닥이다. 봉투·키·eventId를 Kafka 기준으로 만들고, 지금은 HTTP로 묶어 보낸다. 나중에 Kafka로 바꿀 때 이 모듈만 바뀐다.

먼저 끝나야 하는 작업

2

끝나면 확인되는 것

200ms 묶음 전송, 순서 유지, 3회 재시도 후 버림과 지표, 수신 쪽 중복 제거가 테스트로 확인된다.

틀리기 쉬운 상황 같은 체결이 두 번 옴
4
upbit-adapter

upbit-adapter: REST 클라이언트와 요청 예산

왜 이 순서

정확도의 기준인 업비트 원본 값을 가져오는 유일한 통로다. marketdata의 동기화·검사·복구가 모두 이 API에 기대므로 먼저 만든다.

먼저 끝나야 하는 작업

2

끝나면 확인되는 것

/internal/candles·instruments·tickers가 숫자를 문자열로 정확히 주고, 초당 9회와 우선순위를 지킨다.

틀리기 쉬운 상황 같은 값, 다른 자릿수
5
upbit-adapter

upbit-adapter: 웹소켓 수집과 이벤트 발행

왜 이 순서

실시간 입력이다. 업비트 웹소켓 하나로 분봉 8종·체결·티커를 받아 market.* 이벤트로 바꿔 보낸다. 연결·끊김도 이벤트로 알려야 marketdata가 복구를 시작할 수 있다.

먼저 끝나야 하는 작업

3, 4

끝나면 확인되는 것

재연결·일시정지가 동작하고, 메시지가 종류별 이벤트와 키로 발행된다. 종목이 바뀌면 다시 구독한다.

틀리기 쉬운 상황 시작 순서와 재시작
6
marketdata

marketdata: 저장, 구간 동기화, 과거 조회 API

왜 이 순서

정확도의 심장이다. "이 구간을 업비트와 똑같이 만든다"는 일을 CandleSync 한 곳에서만 하고, 확인 구간(coverage)으로 거래 없음과 아직 안 받음을 구분한다.

먼저 끝나야 하는 작업

2 (가짜 소스로 테스트하므로 4 없이도 가능)

끝나면 확인되는 것

DB가 소스와 같아지고(갱신·추가·삭제), 확인 구간이 쌓이며, 과거 조회가 같은 구간을 두 번 받지 않는다.

틀리기 쉬운 상황 같은 값, 다른 자릿수거래가 드문 종목
7
marketdata

marketdata: 이벤트 수신, 진행 중 캔들, 1초 발행

왜 이 순서

사용자가 원한 "1초마다 움직이는 캔들"이 여기서 만들어진다. 체결로 모든 단위를 갱신하되, 업비트 분봉이 더 새로우면 업비트 값이 이긴다.

먼저 끝나야 하는 작업

3, 6

끝나면 확인되는 것

체결·분봉·티커가 규칙대로 반영되고, 1초마다 바뀐 캔들만 chart.* 이벤트로 나간다.

틀리기 쉬운 상황 늦게 온 분봉 이벤트같은 체결이 두 번 옴시작 순서와 재시작
8
marketdata

marketdata: 정합성 검사, 복구, 과거 채우기

왜 이 순서

한 번 맞춘 값을 계속 업비트와 100% 같게 유지하는 장치다. 마감 캔들을 시한 안에 다시 확인하고, 끊긴 구간을 채우고, 장애 구간을 기록한다.

먼저 끝나야 하는 작업

6, 7

끝나면 확인되는 것

1·3·5분봉은 5분, 그 외는 한 주기 안에 검사되고, 5분 끊김이 10분 안에 정확히 메워지며, 대조 검사 도구가 불일치 0을 보고한다.

틀리기 쉬운 상황 거래가 드문 종목시작 순서와 재시작
9
edge-gateway

edge-gateway: 라우팅, WebSocket 허브, viewing 발행

왜 이 순서

브라우저가 들어오는 유일한 입구다. 조회는 marketdata로 넘기고, 받은 chart.* 이벤트를 구독한 세션에만 묶어서 보낸다. 상태가 없어 나중에 여러 대로 늘릴 수 있다.

먼저 끝나야 하는 작업

3 (라우팅 시험은 가짜 marketdata로)

끝나면 확인되는 것

구독한 세션만 캔들을 받고, 세션당 묶음 하나로 전달되며, /api/**가 marketdata로 간다.

틀리기 쉬운 상황 —
10
frontend

프론트: API 계층, 시간 변환, 갱신 규칙

왜 이 순서

화면이 서버 숫자를 바꾸지 않고 보여주게 하는 규칙을 먼저 테스트로 고정한다. 시간은 UTC를 KST로, 갱신은 상태별로 update와 setData를 가른다.

먼저 끝나야 하는 작업

2 (API 형태), 6·9의 응답 형태

끝나면 확인되는 것

시간 변환과 갱신 규칙이 테스트로 고정되고, 재연결 후 구독이 다시 전송된다.

틀리기 쉬운 상황 —
11
frontend

프론트: 차트와 종목 목록 화면

왜 이 순서

앞의 규칙과 API를 묶어 실제 화면을 만든다. 숫자는 서버가 준 문자열 그대로 보여주고, 과거로 넘기면 200개씩 더 불러온다.

먼저 끝나야 하는 작업

10

끝나면 확인되는 것

KRW-BTC 1분봉이 1초마다 움직이고, 단위 전환·과거 스크롤·검색이 되며, 업비트 화면과 같은 분의 값이 같다.

틀리기 쉬운 상황 —
12
검증

함께 실행하기와 완료 기준 검증

왜 이 순서

정확도를 실제 업비트와 24시간 대조해 증명한다. 끊김, 재시작, 실시간 지연, 과거 스크롤까지 완료 기준 7개를 차례로 확인한다.

먼저 끝나야 하는 작업

1~11 전부

끝나면 확인되는 것

불일치 0, 시한 초과 0(장애 구간 제외), 5분 끊김 10분 내 복구, 재시작 무관, 실시간 지연 2초 이내·마감 값 일치·중복 0.

틀리기 쉬운 상황 시작 순서와 재시작
작업마다 테스트를 먼저 쓰고, 실패를 확인한 뒤 구현해서 통과시키고, 커밋하는 순서로 진행합니다.
