# 1·2단계. 계획과 확정

요청: $ARGUMENTS

## 먼저 확인

- `git branch --show-current`가 `worktree-<작업이름>` 꼴인지 본다. 아니면(원래 폴더이면) `.claude/skills/work-start/SKILL.md`를 읽고 0단계부터 한다.
- 작업폴더는 `docs/work/YYYY-MM-DD-<작업이름>/`이다(날짜는 오늘). `docs/work/` 아래에 `-<작업이름>`으로 끝나는 폴더가 이미 있으면 그 폴더를 쓴다.
- 작업폴더에 `plan.md`가 이미 있으면 새로 쓰지 않는다. 요청을 고칠 점으로 보고 "고칠 때"로 간다.

## 계획서 쓰기

1. 무슨 작업인지는 요청과 이 대화에서 가져온다. 요청이 두 가지 이상으로 읽혀서 계획 자체가 달라질 정도면 먼저 사용자에게 한 번 묻는다. 그 밖의 것은 계획서의 "확인이 필요한 결정"에 담는다.
2. `planner` 에이전트(Opus)를 부른다. 에이전트는 이 대화를 보지 못하므로 요청에 다음을 모두 넣는다.
   - 사용자가 한 말 그대로와, 대화에서 정해진 것
   - worktree의 절대 경로
   - 계획서를 저장할 경로: `<작업폴더>/plan.md`
   - 계획서 틀의 경로: `.claude/skills/work-plan/plan-template.md`
   - 이미 살펴본 것이 있으면 관련 파일 경로
3. 돌아온 계획서를 직접 읽고 확인한다. 틀([plan-template.md](plan-template.md))의 모든 절이 채워졌는지, 로직 다이어그램과 ER 다이어그램이 둘 다 있는지, 계획서에 적힌 파일·테이블 이름이 실제로 있는지 본다. 빠졌거나 틀린 것은 고친다.

## 사용자에게 보여 주고 멈춘다

- 계획서 링크
- 핵심 요약 3~5줄
- "확인이 필요한 결정"의 항목과 추천

**확정 전에는 코드를 고치지 않는다.**

## 고칠 때

사용자가 고칠 점을 말하면 계획서를 고치고(작은 수정은 직접, 설계가 달라지는 수정은 `planner`에게 다시 맡긴다) 무엇이 바뀌었는지 알린 뒤 다시 기다린다.

## 확정

사용자가 확정한다고 분명히 말하면 계획서의 상태를 `확정 (YYYY-MM-DD)`로 바꾼다. 질문에 답만 온 것은 확정이 아니다.

## 끝나면

확정됐다고 알린다. 다음 단계는 `/work-implement`이다.
