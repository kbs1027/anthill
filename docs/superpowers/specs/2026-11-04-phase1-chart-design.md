## 1. 배경과 의도

anthill은 **일반인이 가상자금으로 주식 주요 종목과 코인을 사고파는 모의 트레이딩 서비스**다. 공개 운영이 목표다. **[사용자]** 최종 차별점은 캔들에 마우스를 올리면 그 시간대의 커뮤니티 반응을 종합해 보여주는 것이지만, 커뮤니티 데이터는 제휴·법률 검토가 필요해 마지막 단계로 미룬다. **[사용자]**

가장 먼저 만드는 것은 **차트**다. 기준은 하나다: **업비트 화면의 캔들과 시가·고가·저가·종가·거래량이 시간 단위와 무관하게 정확히 일치해야 한다.** **[사용자]** 차트가 틀리면 그 위에 얹을 모의 체결, 수익률, 커뮤니티 반응이 전부 신뢰를 잃기 때문에, 정확도가 이 단계의 유일한 성공 기준이다.

시스템은 **도메인별 서비스**로 나누고, 서비스 사이의 비동기 통신은 **지금은 REST, 나중에 Kafka**로 한다. **[사용자]**

### 2-1. 시장별 데이터 출처 **[승인]**

| 시장 | 출처 | 기준 시세 | 공개 운영 전 필요한 것 |
|---|---|---|---|
| 코인 | **업비트 Open API** | 업비트 | 업비트 상업적 이용 약관 확인 |
| 한국 주식 | 개발: **한국투자증권 Open API** / 공개: **코스콤 시세 라이선스** 또는 증권사 제휴 | **KRX+NXT 통합 시세** | KRX 정보이용계약(법인만 가능) |
| 미국 주식 | **Massive (구 Polygon.io)** | **전체 거래소 통합 시세(SIP)** | 비즈니스 계약(가격 비공개) |

- 한국 주식을 통합 시세로 하는 이유: NXT가 정규장 거래량의 약 27.7%를 차지한다는 실측 정리가 있어, KRX만 받으면 거래량이 크게 빠진다. 한국투자증권은 실시간 체결을 KRX `H0STCNT0`, NXT `H0NXCNT0`, 통합 `H0UNCNT0`로 나눠 제공한다(통합 TR은 22번째 필드명이 달라 위치로 파싱해야 한다는 보고가 있음). 세션당 실시간 등록 41건으로 알려짐(공식 미확인).
- 미국 주식을 SIP로 하는 이유: 거래소가 여러 개라 한 거래소 데이터만 받으면 거래량이 일부만 잡힌다. Alpaca 무료 플랜(IEX 단일 거래소)은 제외.
- 실시간으로 받지 못하는 것과 그 이유는 보고서 04절에 정리돼 있다.

## 3. 1단계 범위

### 목표
- 업비트 **원화(KRW) 마켓 전체**(2026-11-04 기준 299개)의 캔들을 수집·저장한다. **[승인]**
- 지원 단위: **1, 3, 5, 10, 15, 30, 60, 240분 / 일 / 주 / 월**. 가장 작은 단위는 **1분**이다. **[사용자]**
- 진행 중인 캔들은 화면에서 **1초마다** 갱신된다. **[사용자]** (초 단위 캔들을 그리는 것이 아니라, 진행 중 캔들의 값이 1초 간격으로 바뀐다는 뜻)
- 화면: 종목 목록(검색, 현재가, 등락률) + 캔들 차트(단위 전환, 거래량, 십자선 범례, 과거로 스크롤, 실시간 갱신).
- 서비스 3개: **edge-gateway**, **marketdata-service**, **upbit-adapter** (6절). **[사용자 방향, 구성 승인]**
- 실행 환경: 외부에 공개하지 않는다. 로컬 개발 환경과, 24시간 연속 검증용 상시 실행 환경 1개만 둔다. 인증·클라이언트별 요청 제한·HTTPS·백업 같은 공개 운영 요소는 넣지 않는다. **[승인]**

### 하지 않는 것 (1단계)
- 주문·체결, 포트폴리오, 로그인, 보조지표, 호가창 화면
- 국내/해외 주식 어댑터, 커뮤니티 반응
- 초봉 **[사용자]**, 연봉
- Kafka 도입 (계약만 Kafka 기준으로 만든다, 6.3)
- 서비스별 수평 확장 (단, gateway는 상태가 없어 나중에 늘릴 수 있게 둔다)

### 절대 안 되는 것 (이게 생기면 기술적으로 동작해도 실패)
- 마감된 캔들 하나라도 업비트와 숫자가 다른 채로 화면에 남아 있는 것
- 업비트에는 있는 캔들이 우리 차트에서 빠져 있는 것
- 거래가 없던 분을 임의 값으로 채워 넣어, 업비트에 없는 캔들이 생기는 것
- 진행 중인 캔들이 업비트보다 오래된 정보 때문에 뒤로 줄어들어 보이는 것 (업비트의 더 새로운 값으로 맞추는 경우는 예외, 7.3)
- 같은 체결이 두 번 반영돼 거래량이 부풀려지는 것 (서비스 간 재전송, 업비트 재연결·재구독 때문에)

## 4. 업비트 API 실측 결과 (2026-11-04~05 직접 호출)

1. **캔들 시각 경계(KST)**: 일봉 매일 09:00(UTC 00:00), 주봉 월요일 09:00(`first_day_of_period` 제공), 월봉 매월 1일 09:00, 240분봉 09·13·17시…(UTC 기준 4시간 정렬).
2. **거래가 없는 시간에는 캔들이 없다.** KRW-BTC는 1분봉 200개가 200분을 빈틈없이 채웠지만, KRW-OPG는 200개가 3,494분에 흩어져 있었다(약 94% 공백).
3. **1분봉을 합쳐 1시간봉을 만들면** 시가·고가·저가·종가·거래량은 일치하지만 **거래대금(`candle_acc_trade_price`)은 소수점 8번째 자리에서 어긋난다.** → 상위 단위는 업비트에서 단위별로 받는다.
4. **웹소켓 `candle.1m`은 동작한다**(변경 공지의 "초봉만 제공" 문구와 다름). 마감된 분의 마지막 웹소켓 값은 REST와 일치. 단 75초 동안 23건(약 3초 간격)만 왔고, 베타 기능이며, 같은 `candle_date_time`이 여러 번 올 수 있다.
5. **REST 캔들 조회**: 1회 최대 200개, `to`는 **배타적**이고 `2026-11-05T11:23:00`, `...Z`, 공백 구분 형식 모두 UTC로 받는다. 상장 이전 구간은 빈 배열. 캔들·시세 그룹은 **IP당 초당 10회**.
6. **웹소켓 제한**: 연결 요청 초당 5회, 연결당 데이터 요청 메시지 초당 5회. 한 메시지에 여러 종목을 담을 수 있다. 메시지는 바이너리 프레임(UTF-8 JSON)으로 온다.
7. **1초 이하 스트림**: 체결·티커·`candle.1s`는 체결이 생기는 즉시 오지만, KRW-BTC도 30초 중 7~13초에만 갱신이 있었다. **체결이 없는 초에는 어떤 스트림도 새 값을 주지 않는다.** 체결은 몰려서 온다.
8. **티커**의 `opening_price`, `high_price`, `low_price`, `trade_price`, `acc_trade_volume`, `acc_trade_price`는 같은 시점의 당일 일봉과 **수치상 일치**했다. 단 scale이 다르다(`41983565546.39229000` vs `41983565546.3922900000000000`). → 진행 중 일봉은 티커로 만들고, 숫자 비교는 값 기준으로 한다.

## 6. 서비스 구성 **[사용자 방향, 구성 승인]**

### 6.1 서비스와 책임

| 서비스 | 포트 | 책임 | 소유 데이터 |
|---|---|---|---|
| **edge-gateway** | 8080 | 브라우저의 유일한 입구. `/api/**`를 marketdata로 라우팅(Spring Cloud Gateway Server MVC). WebSocket `/ws` 허브: 세션별 구독 관리, 받은 캔들·티커 이벤트를 구독자에게 전달. 보고 있는 종목 목록 발행 | 없음 (상태 없음) |
| **marketdata-service** | 8081 | 시세·차트 도메인. 진행 중 캔들(`LiveCandleBook`), 캔들 저장, 확인 구간(coverage), 소스와의 구간 동기화(`CandleSync`), 정합성 검사·복구·과거 채우기, 화면용 조회 API, 1초 묶음 발행 | PostgreSQL 18 (instrument, candle, coverage, sync_correction) |
| **upbit-adapter** | 8082 | 업비트라는 외부 소스를 감쌈. 업비트 웹소켓 연결·재연결, 수신 정규화와 이벤트 발행, 업비트 REST 호출과 요청 예산(우선순위·초당 9회), 종목 목록 관리 | 없음 |

- 서비스끼리는 코드를 직접 참조하지 않고 공통 라이브러리만 공유한다: `libs/market-contract`(종목 ID, 캔들 단위·경계, 캔들, 값 기준 숫자 규칙, 이벤트 payload, 소스 조회 형식), `libs/event-bus`(이벤트 봉투, 발행·수신 인터페이스, HTTP 전송, 중복 제거 수신함). **[승인]**
- 종목 ID는 소스 접두어를 붙인 문자열이다: `UPBIT:KRW-BTC`, 나중에 `KRX:005930`, `US:AAPL`. **[승인]**
- 주식은 같은 계약을 지키는 어댑터 서비스를 추가해서 붙인다. marketdata는 소스별 기준 URL 설정만 늘어난다.

### 6.2 동기와 비동기의 기준 **[승인]**

**호출한 쪽이 결과를 받아야 다음 일을 할 수 있으면 동기(REST 요청-응답), 아니면 비동기(이벤트).** 동기 호출은 Kafka 도입 후에도 REST로 남고, 비동기만 Kafka로 옮긴다.

| 상호작용 | 구분 | 1단계 방식 | 나중 |
|---|---|---|---|
| 브라우저 → gateway → marketdata: 과거 캔들·종목 조회 | 동기 | HTTP GET | 그대로 |
| marketdata → 어댑터: 소스 캔들 구간 조회 (우선순위 포함) | 동기 | `GET /internal/candles` | 그대로 |
| marketdata → 어댑터: 종목 목록·티커·스트림 상태 스냅샷 | 동기 | `GET /internal/instruments`·`/internal/tickers`·`/internal/stream-status` | 그대로 |
| 어댑터 → marketdata: 체결·분봉·티커·연결 상태·종목 변경 | 비동기 | `POST /internal/events` 묶음 | Kafka `market.*` |
| marketdata → gateway: 진행 중·마감·정정 캔들, 티커 | 비동기 | `POST /internal/events` (1초 묶음) | Kafka `chart.*` |
| gateway → 브라우저: 1초 푸시 | 비동기 | WebSocket `/ws` | 그대로 |
| gateway → marketdata: 지금 보고 있는 종목 | 비동기 | `POST /internal/events` (10초마다) | Kafka `realtime.viewing` |
| marketdata 내부: 정합성 검사·복구·과거 채우기 | 백그라운드 | 스케줄러 + 가상 스레드 | 그대로 |

### 6.3 이벤트 계약 **[승인]**

- **봉투**: `{eventId(UUID), type, version, key, occurredAt, producer, payload}`. payload의 숫자는 문자열.
- **종류**(나중 토픽 이름 = type):

| type | 발행 | 구독 | key |
|---|---|---|---|
| `market.trade.v1` | 어댑터 | marketdata (2단계부터 trading) | 종목 ID |
| `market.candle.v1` | 어댑터 (소스가 분봉을 주는 경우) | marketdata | 종목 ID |
| `market.ticker.v1` | 어댑터 | marketdata | 종목 ID |
| `market.stream-status.v1` | 어댑터 | marketdata | 소스 (`UPBIT`) |
| `market.instrument.v1` | 어댑터 | marketdata | 소스 |
| `chart.candle-update.v1` | marketdata | gateway | 종목 ID |
| `chart.ticker-update.v1` | marketdata | gateway | 종목 ID |
| `realtime.viewing.v1` | gateway | marketdata | gateway 인스턴스 ID |

- **1단계 전송(REST)**: 발행 쪽은 받는 곳마다 보내는 스레드 하나로 200ms마다 쌓인 이벤트를 `POST /internal/events`(JSON 배열)로 보낸다. 순서는 이 단일 스레드로 지킨다. 실패하면 짧게 재시도(최대 3회, 백오프)하고, 그래도 안 되면 버리고 지표(`anthill.events.dropped`)를 올린다.
- **수신 쪽**은 최근 eventId를 메모리에 기억해 같은 이벤트를 두 번 처리하지 않는다(재전송 대비, Kafka의 최소 1회 전달 대비).
- **나중(Kafka)**: 같은 봉투를 레코드 값으로, key를 레코드 키로 쓴다. 바뀌는 것은 전송 구현체와 설정뿐이다.
- **1단계 방식의 한계**: 받는 서비스가 내려가 있는 동안의 이벤트는 사라진다. 시세 이벤트는 marketdata가 시작하거나 어댑터가 다시 연결될 때 소스 REST로 빈 구간을 다시 맞추므로(7.5) 정확도에 영향이 없다. 잃으면 안 되는 이벤트(2단계 주문 체결)는 Kafka 전환 뒤에 도입한다.

## 7. 설계 결정

### 7.1 데이터 원칙 **[승인]**
- **진실의 원천은 소스 캔들이다.** 캔들을 계산하지 않고 소스가 준 값을 단위별로 그대로 저장한다(4-3).
- 가격·거래량·거래대금은 `NUMERIC`으로 저장하고, 서비스 사이와 브라우저로는 **문자열**로 보낸다. 저장·비교·전송 경로에서 float/double 변환 금지. 비교는 **값 기준**(scale 무시, 4-8).
- 시각은 UTC로 저장하고 화면에는 KST로 표시한다. 캔들 식별자는 `(종목 ID, 단위, 캔들 시작 시각 UTC)`.

### 7.2 "거래 없음"과 "아직 안 받음"의 구분 **[승인]**
소스는 거래 없는 시간의 캔들을 주지 않으므로, marketdata는 (종목, 단위)별로 **소스 REST로 확인을 끝낸 구간(coverage)** 을 기록한다. 조회 구간이 coverage 밖이면 어댑터에 조회해 맞춘 뒤 응답한다. coverage 끝 이후 지금까지는, 어댑터 스트림이 coverage 끝보다 먼저 연결돼 그 뒤로 끊기지 않았을 때만 DB 값을 믿는다(스트림 연결 시각은 `market.stream-status` 이벤트와 `/internal/stream-status`로 안다).

### 7.3 실시간 수집 **[승인]**
- upbit-adapter는 업비트 웹소켓 하나로 KRW 전 종목의 **분봉(1~240분) 8종, 체결, 티커**를 구독하고, 각각 `market.candle`·`market.trade`·`market.ticker` 이벤트로 정규화해 보낸다. 연결·끊김은 `market.stream-status`로 보낸다.
- marketdata의 **진행 중 캔들 규칙**:
  - 화면의 진행 중 캔들은 **1초마다** 갱신된다. **[사용자]** 분봉 메시지는 약 3초 간격이라, **체결로 모든 단위(1분~월봉)의 진행 중 캔들**을 갱신하고, 1초마다 바뀐 캔들만 묶어 `chart.candle-update`로 보낸다. 그 1초에 체결이 없으면 보내지 않는다.
  - **업비트가 이긴다.** 분봉 이벤트의 마지막 체결 시각이 우리가 반영한 마지막 체결 시각과 같거나 더 새로우면, 업비트 값을 그대로 쓴다(우리 값이 더 커도 업비트 값으로 맞춤). 분봉 이벤트가 우리가 이미 반영한 체결보다 오래된 경우에만, 고가·저가·거래량·거래대금이 줄어들지 않게 큰 쪽을 유지한다. 같은 시각의 분봉 이벤트 중복은 멱등하게 처리한다. **[승인, 2026-11-07 리뷰 반영]**
  - **체결 중복 제거**: 체결은 업비트 체결 순번(`sequential_id`)으로 중복을 걸러, 업비트 재연결·재구독 때 다시 온 체결을 두 번 반영하지 않는다. 서비스 간 재전송은 eventId로 거른다(6.3).
  - **일·주·월봉**: 일봉은 티커 값을 그대로 쓴다(4-8, 체결마다 옴). 주·월봉은 그 기간의 **마감된 일봉(DB)과 티커의 당일 일봉을 합쳐** 만든다. 시가·고가·저가·종가·거래량은 업비트와 같고(4-3), 거래대금만 끝자리 차이가 생길 수 있어 마감 후 7.4가 맞춘다. 따라서 주·월봉에 체결을 따로 누적하지 않아 오차가 쌓이지 않는다.
  - **지연 목표**: 업비트 웹소켓 수신 시각 기준 **2초 안에** 화면에 반영한다(어댑터 200ms 묶음 + marketdata 1초 묶음).
- 종목 목록은 어댑터가 10분마다 업비트에서 갱신하고, 바뀌면 웹소켓 구독을 다시 하고 `market.instrument`를 보낸다. 상장폐지 종목은 수집을 멈추되 과거 데이터는 보존한다.

### 7.4 마감 캔들 정합성 검사 **[승인]**
- 캔들이 마감되면 어댑터 REST로 다시 받아 저장값과 비교하고, 다르면 소스 값으로 덮어쓰고 기록(`sync_correction`)을 남긴다. 화면을 보고 있는 클라이언트에는 정정 캔들을 다시 보낸다.
- **검사 시한**: 1·3·5분봉은 마감 후 **5분 이내**, 10분 이상 단위는 마감 후 **다음 한 주기 이내**.
- **마감 직후 표시**: 마지막 분봉 이벤트 값을 확정 캔들로 바로 보여준다. '미검증' 표시는 하지 않는다.
- **요청 예산**: 어댑터가 초당 9회(업비트 한도 10회에서 여유 1회)를 우선순위 USER > RECOVERY > RECONCILE > BACKFILL 순으로 나눠 쓴다. 정기 검사 추정치는 약 3.4회/초(299종목). 예산이 모자라면 보고 있는 종목(`realtime.viewing`) → 24시간 거래대금 순으로 먼저 검사한다.
- 운영 지표: 단위별 검사 시한 초과 수, 정정 건수, 검사 지연 시간.

### 7.5 과거 데이터 채우기와 복구 **[승인]**
- **일·주·월봉**은 전 종목 전체 기간을, **분 단위**는 전 종목 **최근 7일**을 미리 채운다. 그 이전은 사용자가 차트를 과거로 넘길 때 받아서 저장한다.
- **복구**: 어댑터가 다시 연결됐다는 이벤트를 받거나 marketdata가 시작하면, (종목, 단위)마다 coverage 끝부터 지금까지를 어댑터에 조회해 채운다. 복구 중에는 정기 검사를 멈추고 예산을 복구에 몰아준다. 5분 끊김 기준 약 2,400회, 약 4분. 끊긴 시점부터 복구 완료까지를 **장애 구간**으로 기록한다(8-2).
- **시작 시 일봉 확보**: marketdata가 시작하면 종목마다 이번 달(또는 이번 주가 더 이르면 그 주) 시작부터 오늘 전까지의 일봉 구간을 먼저 맞춘다. 주·월봉 진행 중 캔들(7.3)을 만들기 위해서다.

### 7.6 화면용 API **[승인]**
- 브라우저는 gateway만 본다. gateway는 `/api/**`를 marketdata로 넘긴다.
- `GET /api/markets`: 종목 ID, 한글명, 현재가, 등락률, 24시간 거래대금 (거래대금 내림차순).
- `GET /api/candles?market&unit&to&count`: 시간 오름차순 캔들 + 진행 중 캔들 + `hasMore`. 숫자는 문자열.
- `WS /ws`: 클라이언트가 `subscribe(market, unit)`·`unsubscribe`·`subscribeTickers`를 보내고, 서버는 `candles`(live·closed·corrected·removed)와 `tickers` 메시지를 보낸다.

### 7.7 화면 **[승인]**
- 좌측 종목 목록(검색, 현재가, 등락률 실시간), 우측 차트(단위 전환, 아래 거래량, 십자선 OHLCV·거래대금 KST 표시, 과거 방향 무한 스크롤, 실시간 갱신).
- 가격은 서버가 준 문자열을 그대로 표시하고 임의로 반올림하지 않는다.
- 거래 없는 시간은 캔들을 채우지 않고 건너뛰어 붙여 그린다. 업비트 웹 차트도 같은 방식인지 검증 단계에서 확인하고, 다르면 업비트 쪽에 맞춘다.

## 8. 완료 기준

1. **일치**: 임의로 고른 종목·단위·기간(거래 많은 종목과 적은 종목 포함)에서, marketdata DB·API의 마감 캔들이 업비트 REST 응답과 **모든 필드가 정확히 일치**하고 **개수도 같다**. 검사 대상은 7.4의 검사 시한이 지난 캔들. 이를 자동으로 검사하는 도구가 있다.
2. **연속 운영**: 24시간 연속 수집 후 1번 검사에서 불일치 0건, 검사 시한 초과 0건. 단 외부 원인(업비트 웹소켓 끊김·점검·REST 오류)으로 생긴 **장애 구간**(끊긴 시점부터 복구 완료까지)은 시한 판정에서 빼고 3번 기준으로 판정한다. 장애 구간은 marketdata가 기록하고 검증 도구가 보고한다. 불일치 0건은 장애 구간에도 그대로 적용된다. **[승인, 2026-11-07 리뷰 반영]**
3. **끊김 복구**: 어댑터의 업비트 웹소켓을 강제로 5분 끊었다 복구하면 **10분 이내**에 빈 구간이 채워지고 1번 검사를 통과한다.
4. **서비스 재시작**: marketdata, upbit-adapter, gateway를 각각 한 번씩 내렸다 올려도(시작 순서 무관) 같은 결과. 체결이 두 번 반영되지 않는다.
5. **실시간**: 진행 중 캔들이 **1초마다** 갱신되고(그 1초에 체결이 있었을 때) 모든 단위(1분~월봉)에 적용된다. 업비트 웹소켓과 우리 `/ws`를 함께 기록하는 비교 도구로 아래를 판정한다.
   - 지연: 업비트 분봉 메시지마다 **2초 안에** 같은 캔들에 대한 우리 푸시가 있다.
   - 마감 값: 우리 마감(closed) 푸시 값이 그 분의 마지막 업비트 분봉 메시지 값과 같다.
   - 중복 없음: 우리 진행 중 푸시의 거래량이 그 분의 마지막 업비트 거래량을 넘은 적이 없다.
6. **경계**: 일·주·월·240분봉의 시작 시각이 4-1과 같고, 화면 축이 KST.
7. **과거 스크롤**: 미리 받지 않은 과거 구간도 스크롤하면 받아와 그려지고 1번 검사를 통과한다.

재시작 시험에서 찾은 장애 구간 기록의 빈틈(값 일치에는 영향 없음):
- upbit-adapter 프로세스가 죽으면 끊김 이벤트를 보낼 수 없어 그 시간이 장애 구간으로 남지 않는다. 다시 켜진 어댑터가 새 연결 시각을 알리면 복구는 돈다.
