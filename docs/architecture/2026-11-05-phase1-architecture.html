02서비스 구성 (지금: REST)

1단계 서비스는 세 개입니다. edge-gateway는 브라우저가 들어오는 유일한 입구입니다. marketdata-service는 시세·차트 도메인을 맡고 DB를 소유합니다. upbit-adapter는 업비트라는 외부 소스를 감싸는 어댑터입니다. 주식은 같은 계약을 지키는 어댑터(kis-adapter, massive-adapter)를 추가하는 것으로 붙고, marketdata-service는 바뀌지 않습니다. 실선은 응답을 기다리는 동기 호출이고, 점선은 보내고 끝나는 비동기 이벤트·푸시입니다.

동기와 비동기를 이렇게 나눴습니다

기준은 하나입니다. 호출한 쪽이 결과를 받아야 다음 일을 할 수 있으면 동기, 그렇지 않으면 비동기입니다. 동기 호출은 Kafka를 도입한 뒤에도 REST로 남고, 비동기만 Kafka로 옮겨 갑니다.

03나중: Kafka로 옮길 때

Kafka를 들이면 비동기 화살표만 Kafka를 거치게 바뀝니다. 동기 조회(과거 캔들, 주문 접수, 잔고 조회)는 그대로 REST입니다. 2단계 이후 서비스들도 이 그림 안에서 이벤트를 발행하고 구독하는 식으로 붙습니다.

바꿀 때 무엇이 바뀌나

이벤트를 보내는 코드는 EventPublisher 인터페이스에만 의존합니다. 지금은 그 뒤에 HTTP로 묶어 보내는 구현을 두고, 나중에 Kafka 구현을 추가해 설정으로 바꿉니다. 이벤트 형식, 키, 소비 쪽 핸들러는 그대로입니다.

061초마다 움직이는 캔들

업비트 분봉 메시지는 약 3초 간격이라 그대로 보여주면 1초마다 움직이지 않습니다. 그래서 체결을 하나하나 받아 marketdata가 모든 단위의 진행 중 캔들(1분봉~월봉)을 메모리에서 갱신하고, 1초에 한 번 바뀐 것만 묶어 gateway로 보냅니다. gateway는 그 종목을 구독한 브라우저에만 전달합니다. 서비스 사이의 화살표는 모두 비동기입니다.

07차트 열기와 과거 스크롤

차트를 열면 최근 200개를, 과거로 스크롤하면 맨 앞 캔들 시각 이전 200개를 요청합니다. 이 흐름은 처음부터 끝까지 동기입니다. marketdata는 이미 확인한 구간이면 DB에서 바로 읽고, 아직 받지 않은 구간이면 어댑터에 조회해 DB를 맞춘 뒤 응답합니다.

08거래 없음과 아직 안 받음

업비트는 체결이 없던 시간의 캔들을 주지 않습니다. 그래서 DB에 캔들이 없다는 사실만으로는 거래가 없었던 건지 아직 받지 않은 건지 알 수 없습니다. 이를 구분하려고 marketdata는 종목·단위마다 소스 REST로 확인을 끝낸 구간(coverage)을 따로 기록합니다.

10끊김 복구

업비트 웹소켓이 끊긴 동안의 캔들은 우리 DB에 없습니다. 어댑터가 다시 연결되면 연결 상태 이벤트를 보내고, marketdata가 종목·단위마다 확인 구간 끝부터 지금까지를 어댑터에 조회해 채웁니다. marketdata 자신이 재시작했을 때도 시작하면서 같은 과정을 거칩니다.

테스트JUnit 5 · Testcontainers · 가짜 소스 · VitestH2, 실제 업비트 호출H2는 NUMERIC·upsert 동작이 PostgreSQL과 달라 정확도 테스트에 맞지 않음. 실제 소스 응답은 계속 바뀌므로 규칙(to 배타적, 최신→과거, 최대 200개)을 흉내 내는 가짜를 씀. 서비스 사이 계약은 공통 라이브러리 타입으로 양쪽 테스트에서 함께 검증.
운영 지표Actuator · MicrometerPrometheus + Grafana1단계는 비공개 검증 단계라 지표 세 개(정정 건수, 검사 지연, 시한 초과)를 /actuator/metrics로 보면 충분.

13데이터 모델

1단계에서 DB를 가진 서비스는 marketdata 하나입니다. 가격·거래량·거래대금은 모두 정밀도 제한 없는 NUMERIC, 시각은 timestamptz(UTC)입니다. 종목 ID에 소스 접두어가 있어서 주식이 붙어도 테이블을 바꾸지 않습니다.

instrument

  • id (키, 예: UPBIT:KRW-BTC)
  • source · symbol
  • korean_name · english_name
  • active · updated_at

상장폐지되면 active만 false로 바꾸고 데이터는 남김

candle

  • instrument_id · unit · start_at (키)
  • open · high · low · close
  • volume · amount

소스 캔들을 단위별로 그대로 저장

coverage

  • instrument_id · unit · from_at (키)
  • to_at

소스 REST로 확인을 끝낸 구간. 겹치거나 맞닿으면 하나로 합침

sync_correction

  • id (키)
  • instrument_id · unit · start_at · kind
  • before · after (jsonb) · detected_at

정합성 검사·복구에서 고친 내용의 기록

이벤트 중복 제거용 eventId는 DB가 아니라 메모리에 최근 것만 보관합니다. 지금 방식에서는 보내는 쪽이 짧게만 재시도하고, Kafka로 바꾸면 컨슈머 오프셋이 그 역할을 함께 맡습니다.

14구현 순서

서비스 분리안을 승인하시면 기존 구현 계획(작업 13개)을 아래 순서로 다시 씁니다. 각 단계 안에서는 지금처럼 테스트를 먼저 쓰고 통과시킨 뒤 커밋합니다.

  1. libs/

    • market-contract: 종목 ID, 단위·시각 경계, 캔들, 값 기준 비교, 이벤트 타입
    • event-bus: 봉투, HTTP 전송(묶음·재시도·순서), 수신함(중복 제거)

  2. upbit-adapter

    • REST 클라이언트와 우선순위 요청 예산
    • 웹소켓 수집·정규화·이벤트 발행, 연결 상태 이벤트
    • /internal/candles·instruments·tickers

  3. marketdata-service

    • 저장소, 구간 동기화, 과거 조회 API
    • 이벤트 수신, 진행 중 캔들 상태 기계, 1초 묶음 발행
    • 정합성 검사·복구·과거 채우기·종목 갱신, 대조 검사 도구

  4. edge-gateway

    • /api/** 라우팅
    • WebSocket 허브와 구독 관리, chart.* 수신·전달, viewing 발행

  5. frontend

    • 지금 계획 그대로 (gateway 하나만 바라봄)

  6. 검증

    • 기존 완료 기준: 24시간 수집 후 불일치 0, 5분 끊김 10분 내 복구, 1초 갱신, 과거 스크롤, 업비트 화면과 비교
    • 추가: 서비스를 하나씩 내렸다 올려도 끝나면 불일치 0

15남은 위험과 확인할 것

높음업비트 시세의 상업적 이용 약관은 아직 확인하지 못했습니다. 공개 오픈 전에 반드시 확인해야 합니다.
높음업비트 웹소켓 캔들은 베타 기능입니다. 바뀌면 진행 중 캔들 갱신이 영향을 받지만, 마감 캔들은 REST 정합성 검사가 5분 안에 바로잡습니다. 이 변화는 upbit-adapter 안에서만 흡수합니다.
높음REST로 보내는 이벤트는 받는 서비스가 내려가 있는 동안 사라집니다. 시세는 복구 과정이 메우지만, 잃으면 안 되는 이벤트(2단계 주문 체결)는 Kafka 전환 전에 들이지 않습니다.
중간서비스가 셋으로 늘어 로컬 실행과 배포가 복잡해집니다. Docker Compose 한 파일로 함께 띄우고, 서비스 간 계약은 공통 라이브러리로 컴파일 단계에서 맞춥니다.
중간업비트 웹 차트에서 거래 없는 분을 어떻게 보여주는지 아직 비교하지 않았습니다. 기본값은 건너뛰고 붙여 그리는 것이고, 검증 단계에서 나란히 놓고 확인합니다.
중간정합성 검사 예산(약 3.4회/초)은 계산한 추정치입니다. 시뮬레이션 테스트와 24시간 실측으로 확인합니다.
낮음주식 쪽은 확인할 것이 남아 있습니다. 한국투자증권의 실시간 분봉 제공 여부와 41종목 한도, Massive의 분 단위 집계 스트림, 코스콤·Massive의 공개용 계약 가격이 그렇습니다. 1단계 범위 밖이지만 주식 단계 일정에 영향을 줍니다.
