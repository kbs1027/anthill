# 4단계. 테스트: 목록을 확인받고 쓴다

사용자가 덧붙인 말: $ARGUMENTS

## 먼저 확인

- `git branch --show-current`가 `worktree-<작업이름>` 꼴인지 본다. 아니면 멈추고 사용자에게 알린다.
- 무엇을 구현했는지 파악한다: 작업폴더(`docs/work/` 아래 `-<작업이름>`으로 끝나는 폴더)의 `plan.md`와 `git diff origin/main`(아직 커밋 전이면 `git status`도)을 본다.

## 하는 일

1. **테스트 목록을 만든다.** 계획서 6절의 후보에서 출발하되 실제 구현에 맞게 고친다. 정상 동작만이 아니라 계획서 5.3절의 예외·경계 상황도 넣는다. 이미 있는 테스트가 확인하는 것은 넣지 않는다.
2. **사용자에게 표로 보여 주고 멈춘다.** 사용자가 확인하기 전에는 테스트 코드를 쓰지 않는다.

   | 확인하려는 것 | 종류 | 테스트 파일 |
   |---|---|---|
   | 수량이 0이면 주문을 받지 않는다 | 단위 | `.../OrderValidatorTest.kt` |

3. **사용자가 확인하면** 빼거나 더한 것을 반영해 테스트 코드를 쓴다. 기존 테스트의 위치와 쓰는 방식을 따른다(백엔드 JUnit 5, 프론트엔드 Vitest).
4. **전체 테스트를 돌린다.** `bash .claude/skills/work-test/run-tests.sh`를 실행한다(백엔드와 프론트엔드 모두). 백엔드 통합 테스트는 Docker가 켜져 있어야 한다. 고치는 동안에는 뒤에 `backend`나 `frontend`를 붙여 한쪽만 돌려도 되지만, 마지막에는 전체를 한 번 돌린다.

5. **실패하면 원인을 찾아 고친다.** 테스트를 지우거나 기대값을 실제 값에 맞춰 바꿔서 통과시키지 않는다. 구현이 틀렸으면 구현을 고친다.

## 끝나면

쓴 테스트와 실행 결과(통과·실패 개수, 실행한 명령의 마지막 출력)를 알린다. 실패가 남았으면 그대로 알린다. 다음 단계는 `/work-e2e`이다.
